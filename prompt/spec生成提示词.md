# 任务

输出一份完整的技术方案设计文档（Markdown），严格包含以下章节：

1. **文档信息** — 版本、日期、负责人、修订记录
2. **设计目标与非目标** — 明确说明本次设计要解决什么、不解决什么
3. **总体架构** — 分层架构图（mermaid），逐层说明模块职责与依赖方向；必须体现「解析层 / 结构化层 / 审查层 / 交互层 / 集成层」的划分
4. **关键技术决策记录（ADR）** — 至少 6 条，每条包含：决策点、备选方案、最终选择、选择理由、放弃理由、该决策的代价。必须覆盖这些决策点：
   - 文档解析如何统一三种格式
   - 条款切分用规则还是模型
   - 锚点定位用什么精度
   - 规则引擎与 LLM 的分工边界
   - 长文档如何分块送模型
   - 审批回写如何保证幂等
5. **文档解析层设计** — 这是本项目的技术核心，必须写到可以直接实现的程度：
   - 三条解析通道（DOCX / PDF 文本层 / 扫描件 OCR）各自的实现步骤与用到的库
   - **定义统一的中间表示（IR）**：给出完整的 Python 类型定义（pydantic 或 TypedDict），说明段落树、层级、坐标、样式字段分别怎么填
   - 三种格式分别能填出 IR 里的哪些字段、哪些字段为空、空字段如何影响下游
   - 解析失败的判定条件与降级链路
6. **条款结构化设计** — 条款切分的实现方案：
   - 切分算法（编号识别、标题识别、长度兜底）的伪代码或真实代码
   - 条款类型分类的实现方式（规则优先还是模型优先，为什么）
   - 元数据字段抽取的实现方式与校验规则
   - 抽不到字段时的处理
7. **锚点定位协议** — 这是本项目最容易翻车的部分，必须写透：
   - 锚点数据结构的完整定义（字段、类型、含义）
   - 三种格式下的锚点生成方式与精度上限
   - 前端高亮渲染方案：DOCX 走结构渲染加字符偏移，PDF 走文本层 bbox，扫描件降级为整页加段落级定位——请评估这个方案并给出更优解或补充细节
   - 「点击风险卡片 → 定位原文」与「点击原文 → 高亮风险卡片」两个方向的接口契约
   - 跨页条款、跨段落条款如何处理
8. **状态机设计** — 任务状态与回写状态的完整定义，用 mermaid stateDiagram 绘制，并给出状态转移表（当前状态 / 事件 / 目标状态 / 副作用 / 失败处理）。必须说明：幂等性如何保证、重试上限、阻塞后如何恢复、并发同一合同如何加锁
9. **数据模型** — 完整建表语句（DDL），以及 mermaid erDiagram。字段要包含索引与约束
10. **接口契约** — 完整 API 定义：
    - 每个接口给出 HTTP 方法、路径、请求体 schema、响应体 schema（用 JSON 示例）
    - SSE 事件类型表（事件名 / 载荷 / 触发时机 / 前端处理）
    - 错误码表（错误码 / 含义 / 前端展示 / 是否可重试）
11. **规则引擎设计** — 规则的数据结构定义（如何把 PRD 第 9 章的规则表变成可执行代码）、规则的加载与匹配顺序、规则版本管理、命中结果如何与 LLM 结果合并、冲突时以谁为准及理由
12. **提示词工程设计** — 四类 prompt 的全部输入输出：
    - 条款切分、元数据抽取、风险判定、修改建议生成
    - 每类必须给出：system prompt 要点、输入变量清单、输出 JSON schema、解析失败的处理、要不要 few-shot 及理由
    - 并说明如何控制幻觉：要求模型引用原文片段、禁止编造法条、依据不足时如何输出
13. **前端实现方案** — 页面路由表、组件树、状态管理方案、文档预览与高亮层的实现细节、与后端联动的请求时序
14. **异常与降级设计** — 一张表列出所有可能的失败点、检测方式、降级动作、用户可见提示
15. **非功能设计** — 性能目标与达标手段、并发控制、安全与权限、审计日志字段、密钥管理
16. **部署与运行** — 依赖服务清单、环境变量清单、启动命令、首次运行需要初始化的数据
17. **测试方案** — 单元测试、集成测试、端到端测试分别覆盖什么；给出「示例合同 → 预期风险清单」的对照表作为端到端测试的判定依据
18. **实施计划** — 按 3 周 / 每天 4 小时拆分任务，每张任务卡片含编号、名称、对应 PRD 需求编号、预估工时、前置依赖、可验证标志
19. **风险与未决问题** — 表格列出技术风险、影响、应对；以及需要产品/法务确认才能继续的问题

# 写作要求

1. **数据结构必须给出真实可用的类型定义**（Python 类型 / JSON schema / DDL），不要只写字段名列表。
2. **接口必须给出真实的 JSON 请求与响应示例**，字段名前后一致。
3. **算法或关键逻辑要给出伪代码或真实代码**，不能只描述"遍历并匹配"。
4. **ADR 章节必须写出被放弃的方案及理由**——这比结论本身更有价值。
5. **明确标出哪些部分可以在 3 周内完成、哪些必须延后**，并给出"最小可交付版本"的技术边界。
6. **涉及第三方库的地方写明具体包名与用途**（例如 `python-docx`、`PyMuPDF`、`jieba`）。
7. 不确定的地方标「待确认」并给出你的建议方案，不要含糊带过。
8. 所有图用 mermaid，所有表格用 Markdown 表格。

# 禁止事项

- 禁止写"可以考虑使用 X 或 Y"这种没有结论的表述，必须给出选择和理由。
- 禁止出现"此处省略""细节略"之类的占位。
- 禁止把 PRD 内容原样搬过来当作设计。
- 禁止设计超出 3 周单人工作量的方案而不加标注。
