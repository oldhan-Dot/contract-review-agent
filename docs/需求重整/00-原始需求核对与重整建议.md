## 1. 这次调整的原则

复杂的主要原因是需求、设计、实现细节和未经确认的指标挤在一起，且 PRD 与 spec 的取舍不一致。解决方式是重新建立来源与职责，不把原始能力删掉，也不因为旧文档写过某个数字就继续把它当成硬性验收。

约束来源按以下次序区分：用户已明确确认的调整、原始任务书、重写后经确认的 PRD、承接该 PRD 的 spec。尚未确认的设计建议不能自行覆盖产品要求。

原文档和既有代码暂时保留。现有测试证明部分代码满足旧约定，不代表旧约定都应进入新版，也不代表系统已完成端到端验收。

## 4. 推荐的技术简化方向（待写入新版 spec 评审）

- 保留现有 FastAPI、Vue、MySQL、LangGraph 和统一解析结果；采用单个后端内的业务模块划分，不引入微服务。
- 保留 LangGraph 的主要流程，节点内部调用普通函数，不把每一个校验或提取动作都变成独立节点。
- 规则负责能稳定验证的条件；模型负责需要语义理解的候选风险与修改建议；对未知、信息不足、模型失败明确提示，不输出“已安全”。
- 示范条款库作为必需业务数据保留。是否需要 embedding、Milvus 或 RAG 由检索需求决定；原文没有指定向量数据库。
- 外部调用集中在模型、OCR、审批适配器；审批 Mock 是正式演示能力，不用假成功记录替代实际请求和回写。
- 先选一种足够支撑进度与状态的通知方式；SSE 与轮询是技术选择，不在 PRD 中绑定实现。
- 不因旧 DDL 已有许多表就要求全部实现 ORM，也不立即删表。新版先按业务实体明确必要数据、结果保存与幂等边界。
- 后台执行仍需考虑并发、进程退出后的任务处置和重试；简化不等于无并发限制或无状态保护。

保留这些技术的理由是现有环境可用、已有可复用模块，并非原始任务书强制选型。

## 5. 分阶段完成，但不降低最终要求

| 阶段 | 可演示成果 | 本阶段结束不能宣称什么 |
|---|---|---|
| A：审查主链 | DOCX 上传、核心结构化、原文点名风险的规则/模型审查、建议、任务结果与基础工作台 | 不能宣称已完成三格式、完整分页高亮或审批闭环 |
| B：格式与证据 | PDF、扫描件成功解析，分页预览、原文与卡片双向定位、异常重试 | 不能用 OCR 失败提示代替成功解析；不能把低精度定位显示成精确定位 |
| C：复核与管理 | 三类角色操作、建议编辑采纳、法务批注、规则与模板维护 | 不能把只读页面当作管理员维护能力 |
| D：集成与验收 | 审批 Mock 触发与回写、两种报告，跨阶段场景验证 | 不能以单个 happy path 代替格式、异常、权限与回写验证 |

以上是交付检查点，不是严格的串行依赖：例如阶段 A 就需准备示例模板和风险用例，阶段 B 的格式试验也可提前完成。实际仍按用户要求逐个模块开发与检查，不一次性写完。

最终沿用原始八条验收能力逐条建立 AC，并补充原文页面、角色、维护操作的对应验收；优先级与阶段分别记录，避免“较晚做”被误读为“不交付”。

## 7. 新文档的组织方式

按两项 Skill 的 11 个主章节编写，控制重复，正文只保留评审和指导开发所需内容。

- 新 PRD：目标、角色、至少八条主流程用户故事、功能与优先级/阶段、非功能目标、流程、三个关键页面、实体初稿、验收、依赖、待确认问题。功能编号使用新版 `FR-01` 等，并保留原文追溯映射；旧编号不静默混用。
- 新 spec：架构、现有/新增技术、模块、实际部署环境、必要数据、关键接口契约、时序、非功能手段、关键 ADR、实现任务与依赖、待明确事项。依据新 PRD，不重新扩张产品范围。
- 拟新增 `01-产品需求文档-重整草稿.md` 和 `02-技术设计规格-重整草稿.md`，不覆盖旧文件。先审 PRD，再写与其一致的 spec。
- 算法长代码、完整 DDL、完整提示词和庞大测试矩阵不在两个正文中反复粘贴；需要时放专题附件或引用实际实现。
- Skill 模板中的性能数字、SLA、多副本/K8s 图例仅是示例，不自动变成本项目约束；不能为了“量化”而编造指标。
