# 送审信息与上传权限调整

> 模块开发记录，保留当时的实现与验证状态。当前需求以 [PRD](../PRD.md) 为准，技术实现以 [Spec](../SPEC.md) 为准；历史章节号不作为当前规范。

日期：2026-10-15。依据重整 PRD R0.2 的 FR-01、FR-19 和 spec R0.1 的上传契约。本模块代码已调整，单元验证通过，真实 MySQL 验证待恢复连接后补做。

## 本模块改什么

对照现有代码发现：旧接口强制填写合同名称，类型可省略为 UNKNOWN，我方角色默认甲方，且法务/管理员也能进入上传逻辑；文件去重没有区分合同类型和我方角色。本次只调整这些上传行为，不接模型、不改变数据库表结构、不启动后台流程。

| 项目 | 新行为 |
|---|---|
| `file` | 必填，目前仍只支持 DOCX |
| `contract_type` | 必填：PURCHASE、SALES、SERVICE、LABOR，不再接受 UNKNOWN |
| `our_party_role` | 必填：A 或 B，不再默认甲方 |
| `contract_name` | 可省略、空字符串或空白；先保存展示占位“待识别合同” |
| 申请人 | 只从已核验的当前身份取得，不读取表单 applicant_id |
| 上传权限 | 仅 BIZ 业务经办人；LEGAL/ADMIN 返回 403，文件暂存前即拒绝 |
| 部门 | 可选，去首尾空白，空白归为未填写 |
| 去重 | 同一申请人、上传来源、未删除任务、文件哈希及大小相同，且合同类型、我方角色、规范化部门相同，才尝试复用 |

名称占位是为了兼容现有 task 表非空字段，不是识别出的合同标题。本模块尚未实现提取后回填任务名称；原文提取与最终保存由后续结果模块衔接。

旧客户端可继续提交可选的金额和币种，保留原有格式校验，用户不必填写。可选名称、金额、币种不是本次去重条件；重复提交返回已存在任务，不覆盖原记录。它们不能冒充已提取的文档事实，后续保存模块需区分送审填写值与提取结果。

## 代码阅读顺序

1. `app/api/tasks.py` 的 `upload_contract` 参数：看哪些字段必填、哪些取消默认值。
2. 方法开头：名称展示占位、部门归一化和文件名检查。
3. `resolve_user` 后的角色检查：核验数据库身份，再限制 BIZ；不相信表单申请人。
4. `previous` 查询：在原有申请人行锁基础上加入类型、角色和部门条件。
5. 后半段仍按原有方式写任务/原件、提交与失败清理。

FastAPI 会先做字段类型和必填校验，格式不对不会查询用户；通过后才进入方法做身份、角色、文件内容及数据库操作。缺少角色时不会自动选 A。

## 请求示例

```powershell
curl.exe -X POST http://127.0.0.1:8000/api/tasks/upload -H "X-User-Id: 2" -H "X-User-Role: BIZ" -F "contract_type=PURCHASE" -F "our_party_role=B" -F "file=@D:/contracts/purchase.docx"
```

名称、主体、金额不需要前端先猜出来。成功响应仍是 HTTP 201，沿用 `{code,message,data:{task_id,task_no,status,duplicated}}`。缺少类型/角色或不合法值返回 HTTP 422、业务码 40001；身份无效 401、权限不足 403。

同一文件改为另一我方角色或合同类型，应产生新任务；同一部门仅增加前后空白，仍视为相同送审上下文。不同申请人不能共享任务。

## 后续边界

| 当前差异 | 后续处理 |
|---|---|
| 审查输入还没有合同类型/我方角色 | 下一模块补齐，从任务上下文传入，不能让模型猜 |
| 标题长度、五年签署日期等旧提取约定 | 单独核对和调整，不在上传模块一起重写 |
| 任务名称回填、部分结果保存、后台状态 | 结果保存/执行器模块完成，不因上传成功就宣称已审查 |
| PDF/OCR 上传、重传/历史文件的去重策略 | 多格式及文件版本模块补齐；本次去重测试不证明未来重传流程已正确 |

本模块保留原文件落盘与失败清理，不删除既有任务或测试，也没有提交/推送 Git。数据库验证恢复前，本模块应标为“代码/单元验证完成，数据库复验待补”。
