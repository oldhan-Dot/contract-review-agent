# 风险结果结构与审查输入

> 模块开发记录，保留当时的实现与验证状态。当前需求以 [PRD](../PRD.md) 为准，技术实现以 [Spec](../SPEC.md) 为准；历史章节号不作为当前规范。

本模块先定义规则需要的输入以及输出风险的数据格式。它不判断任何规则是否命中，不调用模型、不写数据库，也没有接入 `rule_review` 节点。

## 建议阅读顺序

| 文件 | 先看什么 |
|---|---|
| `app/review/context.py` | `RuleReviewInput`：任务标识、原文、条款、元数据如何组成规则输入 |
| `app/review/models.py` | 三个枚举，然后看 `RiskItem` 和 `RiskResult` |
| `tests/unit/test_risk_models.py` | 三类风险的构造及非法证据的拒绝示例 |

输入与结果分开建模，没有复制原文、条款、元数据的字段定义，仍复用现有 `ParsedDocument`、`Clause`、`MetadataResult` 和 `Anchor`。

## 规则输入

`RuleReviewInput` 包含 `task_id`、`file_id`、`review_version`、`document`、`clauses`、`metadata`。

`RuleReviewInput.from_state(state)` 只挑选这些字段，允许 State 中已有摘要或降级信息；必需输入缺失会报校验错误，不能把“上游没有提供 metadata”当成“合同缺少主体信息”。

校验包括：执行标识为数据库范围内的正整数、文档和元数据属于同一原件、条款原文与位置真实、顺序号不重复、父条款在子条款之前存在、长条款子段不越出父范围。任务归属和版本的数据库核验仍由解析节点负责，这里不重复查库。

`review_clauses()` 提供后续规则遍历的条款列表：存在长条款拆分子段时排除对应父记录，避免同一正文审查两次；普通层级父条款仍保留自身正文。完整 `clauses` 不会被删除或改写。`OTHER` 仍在输入中，不能将它当成内容已确认安全。

## 单条风险

`RiskItem` 的主要字段与 PRD、DDL 一致：

| 字段 | 意义 |
|---|---|
| `risk_name` | 风险名称，最多 128 字符 |
| `risk_type` | `CLAUSE_RISK`、`MISSING_CLAUSE`、`METADATA_RISK` |
| `risk_level` | `HIGH`、`MEDIUM`、`LOW` |
| `source` | `rule`、`llm`、`rule+llm` |
| `rule_code` | 命中规则编号；规则/合并来源必填，纯模型来源为空 |
| `clause_index` | 本次切分的条款顺序号，尚未入库，不是数据库条款 ID |
| `clause_type` | 涉及的条款类型，缺项风险用它说明缺少哪类条款 |
| `metadata_keys` | 元数据风险涉及的字段，可多项，例如金额及大写金额数值 |
| `risk_reason` | 风险成因，不能空白 |
| `legal_basis` | 合规依据，默认“依据：待法务确认” |
| `original_text` / `anchor` | 实际原文证据及位置，成对出现 |

不增加数据库主键、人工误报状态、修改建议和冗余定位精度字段。它们属于后续保存、人工复核或建议模块；定位精度当前可直接从 Anchor 读取。

`NONE` 不是一个可保存的风险等级。后续模型如果返回 `NONE`，应由模型接入层决定不生成风险项。

## 三类风险的证据要求

1. **条款风险**：必须有条款顺序号、条款类型、原文与 `anchor_type="clause"` 的 Anchor。结合输入检查时，类型要与条款一致，证据范围必须在该条款内。
2. **必备条款缺失**：必须说明明确的缺失类型，不能填 `OTHER`，不能编造条款顺序号、原文或 Anchor。
3. **元数据风险**：必须引用至少一个不重复的字段，不使用条款顺序号。有观察值证据时使用 `metadata` Anchor，并检查证据与引用字段范围有关联；字段缺失可以无 Anchor。自动标题兜底等本身没有原文定位的字段也不编造证据。

风险原文最多 500 字符，必须与 Anchor 的完整证据文字一致，不接受把长段落首尾拼接后当成连续原文。字段名称、成因和依据会去首尾空白，证据文字不会被清洗，以免位置错位。

## 为什么有两层校验

构造 `RiskItem(...)` 时，Pydantic 校验数据格式及字段之间的约束，例如缺项风险不能有位置。此时对象还没有拿到完整文档，不能独自判断证据是否真实。

随后调用 `item.validate_against_input(context)`，才检查实际原文、条款范围、字段引用。与已有字段结果的 `validate_against_document` 是同样的分工。

这两层校验只证明数据和证据一致，**不证明风险在法律或业务上成立**。是否命中缺失条件、是否适用当前合同类型等由下一步规则执行负责。合规依据按方案应由可信规则配置提供；模型默认占位文字，未来模型接入层不能直接采用模型生成的法条。

## 风险集合

`RiskResult` 用任务 ID、原件 ID、审查版本和 `items` 包住本次结果。`validate_against_input` 核对三个执行标识，并逐项验证证据。

同一集合中，同一 `rule_code + clause_index` 不能重复。缺项和元数据风险的条款顺序号为空，同一规则的多个字段问题需汇总成一项；不同规则命中同一条款可分别保留。这只是内存一致性校验，尚未实现跨执行的数据库幂等或规则与模型结果合并。

空集合允许存在，但不自动计算综合等级、不生成“审查完成”摘要。当前只完成结果结构，不能据此宣称合同没有风险。
