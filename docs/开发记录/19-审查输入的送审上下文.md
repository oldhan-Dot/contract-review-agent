# 审查输入的送审上下文

日期：2026-10-15。依据重整 PRD 的送审角色/合同类型要求与 spec 第 7 章。本次补齐任务记录到 State、再到规则输入的数据传递，不执行实际风险规则，不改变数据库表结构。

## 本模块解决什么

上传已经要求明确合同类型和我方角色，但此前解析节点只返回原文，`RuleReviewInput` 也没有这两个字段。后续规则无法知道该用哪类审查清单，也不能判断甲/乙方哪一方代表我方。

现在的数据流是：

**数据库任务记录 → parse_document 返回上下文 → LangGraph 合并 State → structure_document 保留上下文 → RuleReviewInput 校验。**

| 字段 | 合法值 | 来源 |
|---|---|---|
| `contract_type` | PURCHASE、SALES、SERVICE、LABOR | `ContractTask.contract_type` |
| `our_party_role` | A、B | `ContractTask.our_party_role` |

两项都不默认。未知类型、空角色、中文“甲方”、小写或布尔值等不能直接进入规则审查。

## 文件怎么分工

| 文件 | 本次调整 |
|---|---|
| `app/review/context.py` | 定义两个 Literal 类型别名；`RuleReviewInput` 增加两个必填字段，Pydantic 做运行时校验 |
| `app/graph/state.py` | 增加两个可选 State 字段，复用同一套取值约定 |
| `app/graph/nodes/parse_document.py` | 同一次任务/原件查询取出两个字段，校验后与原文一起返回 |
| `tests/unit/test_review_context.py` | 验证上下文来源、非法值拒绝、会话关闭及真实图内传递 |
| `tests/unit/test_risk_models.py` | 已有风险模型用例显式提供送审上下文，不再依赖缺省 |
| `tests/integration/test_parse_document_node.py` | 测试任务明确填写类型及角色，新增历史缺失数据校验 |

`ContractType` 和 `OurPartyRole` 是允许值的类型别名，不是新增数据库模型，也不是另一份 State。State 中的类型提示与规则输入的运行时校验作用不同。

## 为什么 State 可选，规则输入必填

开始运行图时，可以只传 `task_id`、`file_id`、`review_version`。解析节点查询并校验任务归属、当前版本，再载入真实记录，所以入图前不要求调用方重复填写角色。

到达规则审查时，两项必须已经存在。`RuleReviewInput.from_state(...)` 如果发现缺失或不合法会报校验错误，不会从“甲方写在前面”或标题关键词猜测身份，也不会因此生成一条“合同有风险”的假结论。

即使初始 State 填了与数据库不一致的类型/角色，解析节点仍返回数据库中的值；LangGraph 合并后使用该记录。结构化节点只返回条款和字段，不删除已合并的上下文。

## 解析节点现在的步骤

1. 校验三个内部执行标识。
2. 查询本任务的有效原件和当前任务版本，同时读取类型与角色。
3. 确认版本一致、上下文合法；缺失时明确提示先补充送审信息，不默认成 PURCHASE/A。
4. 关闭数据库会话，再读取 DOCX，避免文件处理期间持有事务。
5. 返回 `document`、`contract_type`、`our_party_role` 三个增量字段，不就地修改输入，也不改变数据库任务状态。

利用的是现有查询，没有增加独立“检查角色”节点或额外任务查询。将来后台执行器仍负责整体执行和版本保护，规则/模板快照留到对应模块实现。

## 历史数据与当前边界

- 历史 UNKNOWN 或空角色明确拒绝；本模块不批量修改旧任务，不自动回填。
- 旧版曾默认保存 A，合法的 A 本身不能证明当时有人明确选择过。历史任务仍需要人工核实，不宣称本模块能够识别所有历史默认值。
- 合同类型和我方角色不等于主体性质。LABOR 也不能直接推出“乙方必然是自然人”；首条主体缺失规则仍需处理企业/自然人的适用性，不能机械要求人人提供企业信用代码。
- 本次仍仅支持 DOCX，风险规则和后台状态机尚未实现。缺失上下文目前抛出明确输入错误；未来执行器需把它映射为可见的受阻/补充信息提示，不能伪装成解析出的风险。
