# 模块 05：解析结果数据结构

> 模块开发记录，保留当时的实现与验证状态。当前需求以 [PRD](../PRD.md) 为准，技术实现以 [Spec](../SPEC.md) 为准；历史章节号不作为当前规范。

本模块按技术方案第 5.2 节定义 `app/parsing/ir.py`。这里的 IR 表示统一中间结果：各解析通道输出相同结构，后面的条款切分和审查无需直接读取 Word 或 PDF。

本次仅实现数据模型及校验，不读取合同、不写数据库，不改变上传接口或 LangGraph 节点的执行行为。下一步实现 DOCX 读取，再让解析节点调用它。

## 先看三个主要结构

| 模型 | 保存什么 | 后续用途 |
|---|---|---|
| `ParagraphNode` | 文本、段落编号、全局字符区间、标题样式、表格标记 | 切分条款，定位风险原文 |
| `QualityReport` | 正文数量、段落数量、可达到的定位精度、解析警告 | 判断解析质量与降级 |
| `ParsedDocument` | 文件 ID、来源格式、段落集合、完整正文和质量报告 | 在节点之间传递完整解析结果 |

`RunSpan` 保存 Word 中加粗、斜体等样式片段。`BBox`、`LineBox` 和 `PageNode` 预留 PDF/OCR 的页面定位信息；它们属于统一格式，本次没有实现 PDF/OCR 读取。

这些模型继承 Pydantic `BaseModel`，用于检查数据格式和字段关系，与继承 SQLAlchemy `Base` 的数据库表模型分开。

## 正文位置如何表示

例如两个段落分别是「甲方」和「乙方」，完整正文必须是 `甲方\n乙方`。

| 段落 index | text | char_start | char_end |
|---|---|---|---|
| 0 | 甲方 | 0 | 2 |
| 1 | 乙方 | 3 | 5 |

字符区间是左闭右开，即开始位置包含在内，结束位置不包含。换行占一个字符，所以第二段从 3 开始。位置按 Python 字符索引记录，不按 UTF-8 字节计算。`slice_text(3, 5)` 返回「乙方」；负索引、越界或结束位置小于开始位置会报错。

DOCX 的段落页码、像素坐标保持空值，`pages` 为空列表。Word 文档页数随排版变化，不能由正文读取过程编造页码。表格中的文字仍作为段落保存，用 `in_table` 和 `table_id` 表示来源，便于保持正文与表格的阅读顺序。

## 自动检查的关系

- IR-01：完整正文必须与段落用单个换行连接后的内容一致。
- IR-02：段落字符位置必须与拼接后的正文一致，拒绝重叠或空洞。
- IR-03：段落列表按文档顺序排列，index 从 0 开始且连续。
- IR-04：行坐标引用的局部字符区间不能超出所属段落。

额外校验段落长度、定位坐标、置信度范围和 DOCX 的页信息约束。技术方案示例先排序再校验 index；本实现要求输入列表本身保持正确顺序，避免切分器直接遍历时读取错误顺序。坐标框须有面积且位于页面内。模型允许空文档结构，空正文如何进入 `blocked` 由下一步解析通道处理。
