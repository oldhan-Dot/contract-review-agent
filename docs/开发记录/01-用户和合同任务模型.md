## 模型解决的问题

以前只有 SQL 表定义；现在可以用 Python 对象访问数据库。例如 `task.contract_name` 对应任务表的合同名称，`task.applicant_id` 对应申请人外键，`task.applicant` 可以读取对应的用户。

用户模型映射 8 个字段，任务模型映射 31 个字段，包含创建时间和更新时间。字段长度、可空性、金额精度、无符号主键和约束均对齐当前 DDL。

关键设计：

- 金额用 `Decimal` 对应 `DECIMAL(18,2)`，不使用 `float`。
- `status` 表示解析与审查进度；`writeback_status` 表示审批回写进度，两者独立。
- `source_event_id` 唯一约束用于后续审批事件接入的幂等控制。
- `Mapped[str | None]` 表示字段可以为空，`Mapped[str]` 表示不可为空。
- 默认状态和时间由 MySQL 生成，插入或刷新后才从数据库读取；不在对象创建时假定这些默认值已生效。
- 本轮只是字段映射，状态变更是否合法由后续状态机负责。

## 连接池、会话和事务

`get_engine()` 提供进程共用的连接池。`get_session_factory()` 缓存的是创建会话的工厂，每次调用工厂获得独立的 Session；并发请求不能共用同一个 Session。

查询示例：

```python
from sqlalchemy import select

from app.core.db import get_session_factory
from app.models import AppUser

# 退出 with 会关闭本次会话，并把连接归还连接池。
with get_session_factory()() as session:
    users = session.scalars(select(AppUser).order_by(AppUser.id)).all()
    for user in users:
        print(user.id, user.display_name, user.role_code)
```

后续 FastAPI 路由会通过 `Depends(get_db)` 获取会话。该依赖负责异常回滚和关闭会话，不自动提交。写入业务需要明确调用 `session.commit()`，或使用 `with session.begin()`：事务块成功则提交，失败则回滚。

`flush()` 与 `commit()` 的区别：前者把 SQL 发往数据库，可以取得自增主键和检查约束，但没有提交事务；后者才确认保存。`autoflush=False` 要求在需要写入时明确调用这些操作。

## 验证

在项目根目录运行：

```powershell
. ./scripts/common.ps1
uv run --locked pytest tests/integration/test_models.py --run-db-tests -q
```

结果：**4 passed**。

1. 用户和任务写入后，通过新会话重新查询，验证申请人关联、金额、默认状态和时间戳。
2. 重复审批事件触发数据库唯一约束，回滚后仍可读取首次成功的记录。
3. 模拟业务异常，验证 `get_db()` 回滚已执行但未提交的写入。
4. 请求正常结束而未提交时，验证写入仍被回滚。

测试使用真实 MySQL。外层事务最终回滚，内层 Session 用 SAVEPOINT 验证提交行为，不保留测试用户和任务。MySQL 自增序号即使回滚也可能产生间隔。默认运行 pytest 会跳过真实数据库测试，需要显式传入 `--run-db-tests`。

Ruff 代码检查通过，两个模型及申请人关联可正确注册。
