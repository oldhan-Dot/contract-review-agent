# 20 — 规则、模型审查与后台执行

日期：2026-10-15。按“先看整体效果”的要求，本次把已有解析、结构化模块接成可运行后台流程。

## 流程

上传保存 pending 任务 → 后台领取 → parse_document → structure_document → rule_review → ai_review → save_results。

`app/services/runner.py` 每秒查询一次数据库，单执行槽处理任务。MySQL 命名锁避免多个后端同时领取；启动时将中断的 parsing/reviewing 任务标为 blocked，管理员可重新审查。每次重试增加 review_version，不覆盖旧版本快照。

## 审查模块

`app/review/engine.py` 集中放首版规则求值和模型适配器，节点文件负责调用和返回 State 更新。

| 规则 | 首版检查 |
|---|---|
| R-SUB-01 | 双方名称，以及明确企业主体的信用代码缺失 |
| R-AMT-01 | 采购/服务合同中我方付款没有验收前置条件的明确表述 |
| R-LIA-01 | 我方承担无上限或无限赔偿责任 |
| R-CON-01 | 有保密约定但期限不明确 |
| R-FOR-01 | 有不可抗力约定但通知时限不明确 |
| R-MIS-03 | 全文未发现保密约定 |
| R-AMT-04 | 字段提取阶段发现大小写金额冲突 |

这是首批演示规则，不能代表完整合同审查覆盖率。修改建议来自示范文本，会明确标记 template；规则依据默认“待法务确认”，没有编造法条或企业信用查询结果。

模型适配器调用配置的 OpenAI 兼容 `/chat/completions`，要求返回结构化 JSON，验证条款编号和逐字证据，再由程序构造 Anchor。超时、无效返回、证据不一致会有限重试，最终 blocked。合同超过首版 45,000 字符限制也会明确受阻，不静默截断全文。

## 保存方式

新增 `sql/ddl/002_workspace.sql` 中的 review_snapshot、review_rule_setting 两张表，后端启动时执行幂等建表。保留已有细分结果表；本轮优先用 JSON 快照保存各节点结果、规则版本、人工意见，后续需要统计分析时再迁移至细分表。没有清空已有数据库。

每个节点完成后保存部分结果；只有规则与模型均成功、最终保存节点提交后才标 completed。模型失败时规则、原文、条款和字段仍可查看。

## 验证和限制

真实 MySQL 联调中，合成采购合同命中 R-AMT-01、R-LIA-01，正常的主体、保密期限和不可抗力通知未误报。当前模型未启用，任务因 AI_NOT_CONFIGURED 受阻，符合预期；尚未验证真实模型效果。

单执行槽是首版实现，尚无分布式任务队列、处理总时限、分批长合同推理及完整观测告警。管理员重试会重新执行整份合同。
