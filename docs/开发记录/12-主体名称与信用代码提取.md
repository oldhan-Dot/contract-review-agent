# 模块 12：主体名称与信用代码提取

> 模块开发记录，保留当时的实现与验证状态。当前需求以 [PRD](../PRD.md) 为准，技术实现以 [Spec](../SPEC.md) 为准；历史章节号不作为当前规范。

新增 `app/structuring/metadata.py`，入口为 `extract_party_metadata(document)`，读取 DOCX 的统一解析结果，填充甲方名称、甲方统一社会信用代码、乙方名称、乙方统一社会信用代码四个字段，返回 `MetadataResult`。

本模块不查询数据库、不调用模型、不执行风险判定；金额、币种、日期等其余目录字段保持未识别，结构化节点仍待整体接入。

## 处理步骤

1. 匹配明确的甲乙方声明，划分各自信息区段。进入下一角色声明、编号条款或正文标题时，停止沿用上一角色。
2. 从声明后的文本读取名称；信用代码优先使用标签中明确的甲乙角色，没有角色时只归入它所在的主体信息区段。
3. 检查常见名称后缀、信用代码长度、字符集和校验位，构造字段并使用实际原文区间生成 `Anchor`。
4. 返回前调用已有原文校验，确认文件、段落、字符位置和证据文字一致。

例如合同中只有乙方代码时，甲方代码保持未识别，不会把首个全局代码同时填给双方。`信用代码（甲方）：...` 作为代码标签处理，不会误识别成公司名称声明。

## 当前支持的明确格式

- `甲方：某某有限公司`、`乙方：某某有限公司`，包括同段并列声明。
- `甲方（买方）：...`、`买方（甲方）：...`、`甲方名称：...`、`甲 方：...`。
- 甲乙方标签独立一段，名称或代码在随后段落中的格式。
- `统一社会信用代码`、`社会信用代码`、`信用代码`、`税号`标签。
- 纵向 Word 表格，例如一行是「甲方 / 公司名称」，下一行是「信用代码 / 代码」。

单独出现的「买方/卖方/供方」不足以可靠确定甲乙方，本模块不固定猜测它们的角色。当前 IR 未保存单元格行列号，连续裸甲乙方并列表头也不按线性顺序分配后续字段，保持未识别并提示人工核对；表格内有明确角色标签的代码仍可使用。

此版本采用确定性格式匹配，复杂倒装表述、隐含角色、跨区引用和其他非标准布局仍需后续扩展或模型辅助。

## 值、原文与警告

信用代码标准值转为大写，原文和锚点保留原始大小写。`validate_uscc` 使用技术方案的 31 字符集、17 位权重和校验位算法；通过校验不代表已查询企业登记或信用状态。

代码校验失败时，保留候选值及真实原文，置信度降至 `0.3` 并记录警告。名称未包含常见组织后缀时同样保留并提示核对是否为自然人或信息不完整，不直接判定合同违法。

找不到可归属的信息、名称为占位符或代码为空白占位符时，字段保持 `is_missing=True`、值为空、置信度为 0、无跳转位置。

同值重复出现时选第一处证据，不作为冲突。不同候选按位置最靠前、同位置最长的顺序选择，并将候选原文列表存入 `field_value_raw`，附人工核对提示。列表最多 1024 字符，无法完整展开时记录警告；标准值超过 512 字符时不截成虚假的名称，而是保持未识别并保存有明确截断提示的候选原文。

上述问题记录在字段的 `warnings` 中，当前没有写入数据库任务的降级状态；后续结构化节点及执行器负责汇总展示。元数据缺失本身不会在本模块触发任务阻塞。

## 调用示例

```python
from app.parsing.docx_channel import parse_docx
from app.structuring.metadata import extract_party_metadata

document = parse_docx("data/samples/采购合同.docx", file_id=1)
metadata = extract_party_metadata(document)
party_a = metadata.get("party_a_name")
print(party_a.field_value, party_a.is_missing, party_a.warnings)
```
